Présentation interne

OxiNote

Application de notes Markdown écrite en Rust, compatible avec les vaults Obsidian existants. Cette page dit ce que le code de la version 0.3.0 fait. Licence : MIT ou Apache-2.0.

Le dépôt

Obsidian est une application propriétaire, Electron et TypeScript, au code source fermé. OxiNote ne la modifie pas. PLAN.md décrit une réimplémentation : mêmes fichiers Markdown, même dossier .obsidian/, et la syntaxe de liens, d’embeds, d’étiquettes et de callouts que ce dossier suppose.

Le texte du dépôt est en français. Le workspace Cargo a sept crates, du vault sur disque jusqu’aux binaires oxinote-app et oxinote. docs/AGENTS.md marque oxi-app « en cours » ; les six autres crates y sont marquées complètes.

Hors périmètre pour l’instant, d’après le plan : Sync, Publish, et les plugins JavaScript déjà écrits pour Obsidian.

Installation et mises à jour

Les publications GitHub contiennent l’application et le CLI. Le workflow .github/workflows/release.yml compile pour :

  • Linux x86_64
  • macOS Apple Silicon
  • macOS Intel
  • Windows x86_64

Sur Ubuntu ou Debian, le paquet .deb place l’application dans le menu et oxinote dans le terminal.

Au démarrage, l’application interroge au plus une fois par jour l’API releases/latest. Si le tag est plus récent, elle télécharge l’archive de la plateforme, la compare à SHA256SUMS.txt et remplace les fichiers installés. La version nouvelle s’exécute au redémarrage. Réglages, About : « Installer automatiquement » (valeur par défaut du code), « Me prévenir seulement », ou « Désactivées ». Une installation .deb sous /usr, un dossier que le processus ne peut pas réécrire, ou une application macOS transloquée, est seulement signalée.

Pour publier une version : mettre version dans Cargo.toml ([workspace.package]) au même numéro que le tag, puis lancer le workflow Release (v0.1.0, ou v0.1.0-rc.1 pour une pré-version) ou pousser un tag vX.Y.Z.

L’application

oxinote-app est une interface eframe / egui. On écrit en Live Preview ou en mode Source, et on lit en mode Lecture. Le registre de commandes couvre la mise en forme, les listes, les cases à cocher, la recherche et le remplacement dans la note, et le pliage. La navigation par titres a deux formes, nommées dans les réglages sommaire flottant et loupe. Les propriétés typées sont un panneau en tête de note.

Les panneaux latéraux montrent l’explorateur, la recherche, les étiquettes, les backlinks, les liens sortants et le plan. Le basculeur rapide et la palette ouvrent une note ou une commande. Les signets, les notes quotidiennes et les modèles ont chacun une commande. Les onglets se répartissent en groupes. Le thème suit le système, ou reste clair, ou sombre.

Neuf plugins de cœur se lisent et s’écrivent dans .obsidian/core-plugins.json : backlinks, signets, notes quotidiennes, graphe, plan, propriétés, étiquettes, modèles, nombre de mots. Un identifiant que ce code ne connaît pas est conservé. Le dossier du vault est surveillé ; les événements sont regroupés avant d’être appliqués.

Un PDF s’ouvre dans un onglet. Le moteur est hayro, en Rust, sans bibliothèque système. L’ouverture vient d’un lien ou d’un embed, avec une page et un zoom. La sauvegarde Git passe par le binaire git du système, dans un fil à part : commit automatique, .gitignore, historique d’une note et restauration de son texte. Il n’y a pas de dépôt distant.

Markdown

Le parseur est pulldown-cmark (CommonMark et GFM), avec un passage supplémentaire pour la syntaxe Obsidian. Chaque élément retenu a un intervalle d’octets dans le fichier d’origine, ce qui permet de réécrire un lien sans déplacer le reste.

Le frontmatter YAML, entre --- sur la première ligne, est converti en JSON. Le code reconnaît aliases / alias, tags / tag, et une valeur qui est exactement un wikilink. Il reconnaît aussi [[cible#sous-partie|libellé]], les embeds ![[…]], les liens Markdown internes, les étiquettes #tag/enfant, les identifiants ^id, les tâches, le surlignage ==…==, les commentaires %%…%%, les callouts > [!type] et les mathématiques. Ces marques ne sont pas relevées dans un span ou un bloc de code, dans les mathématiques, dans un commentaire HTML, ni dans un commentaire %%…%%.

L’édition d’une propriété réécrit le frontmatter et laisse le corps du fichier. Les types lus et écrits dans .obsidian/types.json sont text, multitext, number, checkbox, date, datetime, aliases et tags. Renommer une étiquette vers un nom déjà présent fusionne les deux. Renommer une note ou un dossier met à jour les liens qui les visent.

Un lien est résolu dans cet ordre : chemin exact, puis nom de fichier unique. S’il reste plusieurs fichiers, le plus proche du dossier source l’emporte, puis l’ordre alphabétique.

Commande oxinote

Chaque sous-commande prend le dossier du vault en premier argument. La recherche accepte tag:, path:, file:, une phrase entre guillemets, -exclure, OR et /regex/.

CommandeEffet
statsNotes, pièces jointes, liens, étiquettes, orphelines, mots.
searchLignes chemin:ligne: texte, ou JSON.
backlinks, links, unresolvedLiens entrants, liens sortants, cibles absentes.
tags, tagComptes, arbre, renommage, ajout ou retrait.
props, propPropriétés du vault ; écriture ou suppression dans une note.
orphans, findNotes sans lien ; recherche floue par nom, chemin ou alias.
graphJSON ou Graphviz, graphe local, coordonnées force-directed en option.
renameDéplace une note et met à jour les liens. --dry-run n’écrit rien.
dailyOuvre ou crée la note du jour et affiche son chemin.
exportSite HTML statique. Les wikilinks deviennent des liens relatifs.
 
cargo test --workspace
cargo run -p oxi-cli -- stats examples/sample-vault
cargo run -p oxi-app -- examples/sample-vault

examples/sample-vault/ sert aux tests, au CLI et à l’application. Les tests qui écrivent en copient le contenu dans un dossier temporaire.

Le YAML du frontmatter devient un serde_json::Value. La recherche est un index inversé du dépôt. PLAN.md cite Tantivy comme piste ultérieure, pas comme moteur en place. Le workspace interdit unsafe.

Prévu dans PLAN.md

La feuille de route, après ce que le plan marque comme fait, n’est pas dans l’application aujourd’hui :

  • Bases : vues tableau au format .base.
  • Canvas : tableau blanc au format .canvas.
  • Citations : BibTeX ou Zotero, [@clé], note de lecture.
  • PDF, suite : sélection, recherche de texte, embeds dans le Live Preview, annotations. Le lecteur en onglet existe déjà.
  • Git distant : push et pull. La sauvegarde locale existe déjà.

La phase 3 du plan cite aussi une API de plugins en traits Rust puis en WASM, des thèmes et des snippets CSS, et un objectif de temps de réponse sur 10 000 notes. Le guide des agents ne les marque pas livrés. Le thème clair, sombre ou système est dans settings.rs ; cette page ne décrit pas de chargeur de thème CSS.
